## 분산락을 사용하면 rollback까지 보장할 수 있나요?

보장하지 않는다. 분산락은 상호 배제를, 롤백은 트랜잭션의 원자성을 제공한다. 서로 다른 속성이고 한쪽이 다른 쪽을 포함하지 않는다.

## 락과 롤백이 각각 지키는 범위

분산락은 여러 서버가 공유하는 저장소에 락 소유 상태를 원자적으로 기록해 동시 진입을 막는다. Redis라면 `SET key value NX PX ttl` 한 번으로 "키가 없을 때만 만들고 ttl 뒤 자동 삭제"를 한다. 보장하는 건 락을 잡은 실행이 하나뿐이라는 것과, 보유자가 죽어도 ttl 뒤에 풀린다는 것뿐이다. 임계 구역 안의 작업이 성공했는지, 실패하면 무엇을 되돌릴지, ttl이 지난 뒤에도 이전 실행이 돌고 있는지는 모른다.

롤백은 그 트랜잭션에 참여한 DB 연산만 되돌린다. 외부 API 호출, 메시지 발행, 다른 저장소 쓰기는 대상이 아니다. 그래서 한 요청 안에 보장 범위가 다른 세 구간이 겹친다.

```kotlin
val lock = redisson.getLock("stock:$productId")
if (!lock.tryLock(3, 5, TimeUnit.SECONDS)) throw LockAcquireException()
try {                                        // 락 구간 시작: 상호 배제
  txTemplate.execute {                       // 트랜잭션 구간 시작: 원자성
    val stock = stockRepository.findForUpdate(productId)
    stock.deduct(qty)
    orderRepository.save(Order(...))
  }                                          // 커밋. 이후 DB 변경은 확정
  paymentClient.approve(orderId, amount)     // 락 안, 트랜잭션 밖. 되돌릴 수 없음
  eventPublisher.publish(OrderPlaced(...))   // 되돌릴 수 없음
} finally {
  lock.unlock()                              // 락 구간 끝
}
```

| 구간 | 보장 | 실패 시 |
|---|---|---|
| 락 구간 | 동시에 하나만 진입 | 락은 `finally`로 정상 해제됨. 그뿐이다 |
| 트랜잭션 구간 | DB 변경의 원자성 | 롤백으로 원상복구 |
| 외부 호출 | 없음 | 아무도 되돌리지 않음 |

결제 승인 뒤에 예외가 나면 락은 풀리고 DB는 이미 커밋돼 있고 결제만 승인된 채 남는다. 락은 이 상황에 아무 영향을 주지 않는다.

## 이어서 따라오는 질문

### DB transaction과 lock release 순서는 어떻게 잡아야 하나

락 획득 → 트랜잭션 시작 → 커밋 → 락 해제. 락 구간이 트랜잭션을 완전히 감싸야 한다.

`@Transactional` 메서드 안에서 `tryLock`/`unlock`을 부르면 이 순서가 깨진다. 본문 끝에서 `unlock`이 먼저 실행되고 커밋은 AOP 프록시가 그 뒤에 한다. 커밋 전에 락이 풀리니 다음 요청이 옛 값을 읽고 두 요청 모두 차감에 성공한다. 락 메서드와 트랜잭션 메서드를 나누거나, `TransactionTemplate`으로 트랜잭션 범위를 락 안에 명시한다.

### Lease time이 너무 짧거나 길면 어떤 문제가 생기나

짧으면 작업 중에 락이 풀려 중복 진입이 생기고, 길면 장애 시 락이 그만큼 오래 남는다. lease는 장애 시 락이 영구히 남지 않게 하는 안전장치라, 작업 시간보다 넉넉히 잡고 작업 시간을 그 아래로 제한한다. Redisson watchdog은 lease를 지정하지 않으면 보유자가 살아 있는 동안 자동 연장하는데, 작업이 멈춘 채 프로세스만 살아 있으면 락이 안 풀린다.

### 외부 API 호출이 포함된 로직은 rollback을 어떻게 설계하나

롤백 대신 순서와 보상으로 설계한다. 되돌릴 수 있는 것을 먼저, 되돌릴 수 없는 것을 나중에 둔다.

DB를 `PENDING`으로 커밋한 뒤 외부 호출을 하고, 실패하면 `FAILED`로 바꾸는 후속 트랜잭션을 돌린다. 외부 승인이 먼저여야 하면 반대로, DB가 실패했을 때 취소 API를 부르는 보상 흐름을 둔다. 보상 호출도 실패할 수 있으니 멱등키를 붙여 재시도할 수 있게 한다. 중간 상태를 데이터로 남겨야 배치나 정산 대사가 미완료 건을 찾는다.

## 락 없이 되는지부터 본다

| 지키려는 것 | 도구 | 분산락 필요 여부 |
|---|---|---|
| 같은 자원에 대한 동시 갱신 | 조건부 UPDATE (`WHERE stock >= :qty`), `SELECT ... FOR UPDATE` | 불필요. 단일 DB면 DB 락이 더 싸다 |
| 같은 요청의 중복 실행 | 멱등키 + unique 제약 | 불필요. 제약 위반이 곧 중복 감지 |
| DB 밖 작업을 포함한 구간의 동시 진입 | 분산락 | 필요 |
| 외부 호출 이후 실패의 복구 | 보상 트랜잭션, Outbox, 재시도 | 무관. 별도 설계 |

분산락을 떠올리는 상황 중 상당수는 단일 DB 안에서 끝나는 갱신이다. 이때는 조건부 UPDATE가 더 정확하다. 영향 행 수가 0이면 실패로 처리하면 되고, 락 만료·해제 누락·Redis 장애 같은 실패 모드가 없다.

결과가 행의 존재 여부로 표현되면 unique 제약이 곧 상호 배제다. 주문번호당 결제 레코드 하나, 사용자당 쿠폰 하나 같은 경우 동시에 INSERT하면 한쪽만 성공하고, 실패한 쪽은 기존 행을 읽어 같은 응답을 돌려준다. 수량 차감처럼 결과가 행의 값이면 unique 제약은 못 쓰고 조건부 UPDATE가 그 역할을 한다. 분산락은 DB 밖 작업까지 직렬화해야 할 때 필요하다.

나도 등록 API에서 첨부 파일 귀속은 트랜잭션 안에 두고, 외부 채널 알림은 `@TransactionalEventListener(AFTER_COMMIT)`로 커밋 뒤로 뺐다. 기준은 실패했을 때 롤백이 되돌려 주는가였고, 이 경계는 락 유무와 상관없이 먼저 그어야 했다. 경위는 [무엇을 트랜잭션 안에 넣고 무엇을 커밋 이후로 미룰 것인가]({% post_url 2026-09-10-transaction-boundary-and-after-commit-events %})에, 반드시 전달돼야 하는 것만 Outbox로 올린다는 기준은 [이벤트 전달·정합성 패턴]({% post_url 2026-07-01-event-delivery-consistency-patterns %})에 적었다.

## 정리

- 분산락은 동시 진입만 막는다. 롤백은 트랜잭션이 하고, 그 범위는 트랜잭션에 참여한 DB 연산까지다.
- 락은 트랜잭션을 감싸야 한다. `@Transactional` 안에서 unlock하면 커밋 전에 락이 풀린다.
- 외부 호출과 메시지 발행은 롤백 밖이라 커밋 이후 발행, `PENDING` 같은 중간 상태, 멱등한 보상으로 따로 설계한다.
- 단일 DB 안의 갱신은 조건부 UPDATE나 unique 제약으로 락 없이 푼다. 분산락은 DB 밖 작업까지 직렬화해야 할 때만 쓴다.
