등록된 `report` 가 있고, 그것을 근거로 만들어지는 `request` 가 있다. 한 `request` 는 `report` 한 건에만 연계되고, 한 `report` 에는 여러 `request` 가 붙는다. 화면에서는 `report` 목록에 "연계 요청 3건" 같은 숫자가, 상세에는 연계된 `request` 요약 목록이 나와야 했다. 이 스키마를 짜면서 두 가지를 정했다. 참조 컬럼을 어느 쪽에 둘지, 그리고 연계 건수를 컬럼으로 저장할지.

## 참조 컬럼은 request 쪽에 뒀다

`report` 쪽에 `request_id` 를 두면 여러 요청 중 하나만 담을 수 있다. `request` 쪽에 `report_id` 를 두면 한 요청이 두 보고를 가리키는 상태가 컬럼 타입만으로 막힌다.

조인 테이블도 검토했지만 두지 않았다. 1:N 에 조인 테이블을 쓰면 "한 요청에 보고 두 건"을 스키마가 허용하게 되고, 그 제약을 애플리케이션 코드로 다시 지켜야 한다.

기존 행은 전부 `NULL` 로 남겼다. `NULL` 이 곧 "연계 없음"이라 백필이 필요 없었고, 대부분이 `NULL` 인 컬럼이라 부분 인덱스(`WHERE report_id IS NOT NULL`)가 잘 맞았다.

## 연계 건수는 저장하지 않았다

목록에 카운트 배지가 필요하다는 요구를 받고 처음엔 `report` 에 `linked_request_count` 컬럼을 떠올렸다. 그런데 이 값을 바꿔야 하는 경로를 적어 보니 요청 생성, 요청 삭제, 연계 해제, soft delete 된 요청의 복구까지 최소 네 곳이었다. 하나만 빠뜨려도 값이 틀리는데, 틀려도 예외가 나지 않는다. 화면은 "3건"인데 열어 보면 2건인 상태가 되고, 언제부터 틀렸는지 알 수 없으니 전량 재계산 말고는 복구할 방법이 없다. 앞으로 요청을 만들거나 지우는 코드를 추가하는 사람도 매번 이 컬럼을 기억해야 한다.

저장하는 게 맞는 경우도 있다. 읽기가 쓰기보다 압도적으로 많거나, 그 값이 정렬·필터 조건이거나, 집계 쿼리가 실제로 느릴 때다. 이번엔 셋 다 아니었다. 카운트는 배지로만 나오고 정렬·필터에 쓰이지 않는다. 참조 컬럼에 부분 인덱스가 있어 집계가 가볍고, 조회도 한 페이지 단위다. 나중에 "연계 건수 많은 순 정렬" 같은 요구가 들어오면 그때 다시 따져야 한다.

컬럼 대신 스키마에 저장하지 않기로 한 이유를 주석으로 남겼다. 안 적어 두면 다음 사람이 "왜 이걸 매번 세지?" 하고 컬럼을 추가할 것 같았다.

## 대신 목록 집계를 한 번으로 묶었다

매번 세기로 하면 목록 20건에서 행마다 세는 순간 N+1 이 된다. 그래서 목록 조회는 페이지를 먼저 가져와 id 목록을 뽑고, 그 목록으로 `GROUP BY` 집계를 한 번 날린 뒤 `Map<Long, Long>` 으로 붙였다. 첨부 유무도 id 집합을 한 번에 던지고 `Set` 으로 받아 `in` 으로 판정했다.

```kotlin
val ids = page.content.map { it.id }
val linkedCounts = countLinkedRequests(ids)   // 쿼리 1회
return page.map { it.toListItem(linkedCount = linkedCounts[it.id] ?: 0) }
```

`GROUP BY` 결과에는 연계가 0건인 키가 아예 없다. 그래서 호출부에서 `?: 0` 으로 채운다. 집계 반환은 `List<Array<Any>>` 를 받아 `associate` 로 Map 을 만드는 형태라 타입이 이 사실을 알려주지 않는다. 0건은 화면에서 빈칸이라 실수해도 티가 안 나서, 메서드 주석에 "연계가 0건인 대상은 행 자체가 없다 — 호출부가 0 으로 채운다"를 적었다.

같은 목록 경로의 to-one 연관 N+1 은 [계산 프로퍼티 뒤에 숨은 N+1]({% post_url 2026-09-10-hidden-n-plus-one-behind-computed-property %})에 따로 정리했다.

## soft delete 에서도 파생값이 편했다

이 테이블들은 soft delete 라 모든 집계·조회에 `deleted_at IS NULL` 이 붙는다. 카운트를 저장했다면 삭제와 복구가 모두 카운터를 건드려야 했고, 복구는 특히 잊기 쉽다. 파생값은 조건 하나만 맞으면 삭제든 복구든 자동으로 맞는다.

삭제 가드도 같은 식으로 짰다. 연계된 요청이 있으면 작성자는 보고를 지울 수 없는데, 이 판정을 저장된 카운트가 아니라 실제 조회 결과로 한다. 저장값으로 판정하면 값이 어긋났을 때 지우면 안 되는 게 지워진다. 화면 숫자 하나 틀리는 것과는 무게가 다르다.

결국 저장 여부는 성능보다 그 값을 누가 계속 맞게 유지하느냐의 문제였다. 연계 건수는 컬럼 대신 부분 인덱스와 배치 집계로 해결했다.
