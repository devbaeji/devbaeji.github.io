⑤ 트랜잭션 생명주기 — 발행/적재/실시간 타이밍

▶ 로 한 단계씩. 왼쪽 막대 = 트랜잭션 살아있는 구간 / 오른쪽 = 그 순간 실행되는 실제 코드(노란 줄). 교육용 일러스트는 작업자 출근(check-in) 예시 — 원본 가정대로 AttendanceHistory에 마커가 붙었다고 가정한다. 단 현재 코드에서 실제로 QueuePublishable 마커가 붙은 건 TicketHistory 하나뿐이다.

📡 전체 인과 흐름 — 비즈니스 DB → audit history → 큐 이벤트 로그
① 비즈니스 DB INSERT/UPDATE 도메인 변경(티켓 status·assignee / 예시: 출근 Attendance)을 T1 안에서 저장. 이게 모든 것의 원인(트리거).
▶
② audit history INSERT ①이 커밋되면 그 사실을 history 테이블에 기록 기존
▶
③ 큐 이벤트 로그 발행 같은 변경을 ActiveMQ로 발행 이번 PR
※ ②와 ③은 순서대로 의존하는 게 아니라, ①의 커밋이라는 같은 원인에서 갈라져 나온 형제(독립 구독자)다. ③이 ②의 완료를 기다리지 않음.
아래는 그 갈라짐(fan-out)을 트랜잭션·이벤트버스 관점으로 본 그림
🟠 발신자 (PRODUCER)
eventPublisher.publishEvent(EntityHistoryEvent)
EntityHistoryListener(엔티티에 @EntityListeners로 물림)가 flush 때 1번 던짐 · 수신자가 누군지 모름. 이때 diff(changes)는 이미 ActivityChangeHolder에 담겨 있어 함께 실어 보냄.
🔵 우체통 (이벤트 버스)  커밋 성공까지 보류 → AFTER_COMMIT에 같은 이벤트를 구독자에게 차례로 배달 (T1 밖)
🟣 수신자 ① (CONSUMER)
EntityHistoryEventHandler기존 audit · ②
@AFTER_COMMIT REQUIRES_NEW → 새 T2
DB에 history INSERT를 해야 함. 그런데 T1은 이미 끝나 열린 트랜잭션이 없음 → DB 쓰기용 트랜잭션 필요 → REQUIRES_NEW로 새 T2를 연다. 발신자가 누군지 모름.
🟢 수신자 ② (CONSUMER)
ActivityEventRelay이번 PR · ③
@AFTER_COMMIT @Transactional 없음
큐에 발행만 하고 DB는 안 씀 → 트랜잭션 자체가 불필요 → 아무 tx도 안 연다. 비즈니스 T1과 엮일 여지가 원천적으로 없음. (마커 QueuePublishable 붙은 것만 발행 — 현재 실제 마커는 TicketHistory뿐, 아래 예시는 AttendanceHistory에 마커가 붙었다고 가정)
∴ 발신자는 "리스너를 안 고치고 수신자만 추가"가 가능 — ③(큐)은 ②(audit)를 건드리지 않고 우체통에 구독자 1개 더 붙인 것뿐.
현재 활성 트랜잭션: 없음
T1 (비즈니스) T2 (REQUIRES_NEW) 트랜잭션 없음

왜 "엮이지 않나" — 리뷰어 코멘트 해설

    
💬 리뷰어 코멘트: "잘못 묶이면 원래 있는 트랜잭션과 엮이는 거 아닌가 모르겠습니다. REQUIRES_NEW는 트랜잭션을 하나 더 만들어서 괜찮을 듯한데."

    
"엮인다"는 건 = audit/큐 작업이 비즈니스 트랜잭션(T1) 안에 함께 묶여서, 부가작업이 실패하면 본 비즈니스(출근·티켓변경)까지 롤백되는 상황. 같은 트리거를 어떻게 다느냐에 따라 결과가 갈린다.

      리뷰어 말의 핵심:

      • "잘못 묶이면 원래 트랜잭션과 엮인다" = ①번 걱정. 부가작업을 T1 안에 두면 그게 실패할 때 본 비즈니스까지 날아간다.

      • "REQUIRES_NEW는 트랜잭션 하나 더 만들어서 괜찮을 듯" = ③번 해법. DB에 써야 하는 audit은 새 트랜잭션 T2를 따로 열어 T1과 분리 → 서로 영향 없음.

      • 그리고 우리 큐 발행(④)은 한 발 더 나아가 DB를 안 쓰니 트랜잭션 자체가 필요 없다 → REQUIRES_NEW조차 안 붙임 → T1과 엮일 일이 애초에 없음.
    

    
우리 큐 발행(④)에서 diff는 언제?
큐 발행은 DB를 안 써서 tx 자체가 필요 없다. 단 diff 계산은 그 전, T1 안의 flush(EntityHistoryInterceptor.onFlushDirty)에서 끝나며 ActivityChangeHolder에만 담아둔다 — 이건 메모리 홀더라 DB 쓰기가 아니다. 발행은 AFTER_COMMIT, diff는 커밋 전 flush — 타이밍이 다르다.


    
    
📚 현업 표준 — 이벤트 전달·정합성 패턴 (정보)

    
핵심 원칙: "정답은 데이터 중요도가 정한다." 정합성을 일부 포기하는 것도, 절대 안 포기하는 것도 둘 다 표준이다.
      audit·알림·분석류는 흔히 best-effort로 싸게 가고, 돈·주문·재고·정산처럼 반드시 전달돼야 하는 것만 Outbox/CDC로 승격한다.


    
⚠️ Dual-write 안티패턴
"비즈니스 DB 커밋"과 "이벤트 발행"을 서로 다른 작업으로 따로 하면, 커밋은 됐는데 발행이 실패하는 틈이 생긴다(정합성 깨짐). 지금 우리 구조(AFTER_COMMIT 발행)가 바로 이 형태(G1). 보장이 필요하면 아래 Outbox/CDC로 이 안티패턴을 제거한다.


    

      
① Best-effort 비동기 발행 정합성 일부 포기 ≈ 지금 우리 구조

      커밋 후(AFTER_COMMIT) 발행/기록을 따로 시도하고 실패는 runCatching으로 로그에 흡수. 부가기능이 본 비즈니스를 못 막게 decoupling이 목적.
      장점: 단순·빠름·본 비즈니스 보호. 단점: 드물게 조용한 유실/불일치(커밋 성공 + 기록 실패).
      적합: 감사로그·활동피드·분석·알림 등 한두 건 빠져도 되는 데이터.
      
→ 현재 audit(EntityHistoryEventHandler, T2)·큐 발행(ActivityEventRelay)이 여기에 해당.

    


    

      
② Transactional Outbox 전달 보장 정합성 보장

      비즈니스 데이터 + 이벤트(outbox 행)를 같은 트랜잭션(T1)으로 INSERT → 커밋되면 이벤트도 무조건 함께 남음(원자적).
      별도 폴러/릴레이가 outbox를 읽어 큐로 발행하고 성공 시 published_at 마킹(성공할 때까지 재시도).
      핵심: T1 안엔 로컬 INSERT만(안전), 위험한 원격 발행은 T1 밖으로 미룸 → 리뷰어의 "엮임 회피" 원칙도 지킴.
      마이크로서비스의 사실상 표준 레시피.
    


    

      
③ CDC (Change Data Capture) 전달 보장 대규모 적합

      Debezium 등이 DB 트랜잭션 로그(binlog/WAL)를 직접 읽어 Kafka로 발행. outbox 테이블 없이도 "커밋된 것 = 곧 이벤트"라
      정합성이 DB 커밋에 자동으로 묶임. 장점: 앱 코드 거의 무변경·고처리량. 단점: 별도 인프라(Debezium/Kafka) 운영 부담.
      대규모·다수 서비스 환경에서 가장 흔한 실전 스택.
    


    

      
④ Event Sourcing 특수 도메인

      상태를 저장하는 대신 이벤트 자체를 진실의 원천으로 삼고, 상태는 이벤트를 재생해 만든다.
      정합성·이력추적이 강력하지만 도입·운영 비용이 큼. 금융 원장 등 특수 도메인에서 선택적으로.
    


    
💡 "exactly-once 전달"은 신화다
분산 시스템에서 정확히 한 번 전달은 사실상 불가능 →
      현업의 실무 목표는 at-least-once 전달(재시도로 안 잃음) + 멱등 소비자(eventId로 중복 무시) = exactly-once "효과". 결제 시스템조차 이 방식을 쓴다.


    
✅ 우리 결론
활동 이벤트가 분석/피드용(유실 용인)이면 ①(지금 구조)로 충분.
      전달 보장 + 정합성이 목표라면 ②Transactional Outbox로 간다(이벤트 캡처를 T1 안으로).
      기존 audit 재활용은 audit의 T1↔T2 정합성 틈을 물려받으므로 보장엔 부적합.
